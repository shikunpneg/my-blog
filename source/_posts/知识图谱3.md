# 两种基于Tableaux算法的reasoner的源码分析（2）

## FaCT++源码分析

### 第一站：图纸与积木 —— dlCompletionTree.h 和 dlCompletionGraph.h

**为什么先读这个？**

`Reasoner` 类里有三个最重要的成员：`CGraph`（完工图）、`curNode`（当前节点）和 `TODO`（待办清单）。如果不先搞清楚"节点"长什么样、"图"怎么存，后面所有的 `createOneNeighbour` 和 `addToDoEntry` 都是空中楼阁。

#### 1. dlCompletionTree.h —— 节点的定义

在 Tableau 算法里，节点最核心的职责就是**装着它所属的概念集合**（比如，这个个体属于 `A`，也属于 `∃R.B`）。在 FaCT++ 里，这个概念集合通常叫 `Label` 或 `CGLabel`。

**核心成员变量：**

```cpp
CGLabel Label;                     // 概念标签集合（所有断言的集合）

#ifdef RKG_IR_IN_NODE_LABEL
IRInfo IR;                         // 不等式关系信息（用于处理"不同个体"）
#endif

ArcCollection Neighbour;           // 角色边列表（指向其他节点）
TSaveList<SaveState> saves;        // 历史状态栈（用于回溯）

unsigned int id;                   // 节点唯一 ID
BipolarPointer Init;               // 创建该节点时的初始概念

const DlCompletionTree* Blocker;   // 当前阻塞该节点的节点（若有）
DepSet pDep;                       // 用于 purge 操作的依赖集

unsigned int curLevel;             // 当前级别（用于回溯）
CTNominalLevel nominalLevel;       // 名义级别（0=名义，-1=块状）

// 布尔标志（位域）
bool flagDataNode : 1;             // 是否数据节点（字面量）
bool cached : 1;                   // 是否已缓存（用于优化）
bool pBlocked : 1;                 // 是否被永久阻塞（purge）
bool dBlocked : 1;                 // 是否被直接阻塞（directly）
bool affected : 1;                 // 是否因阻塞变化而受影响
```

**对应 Tableau 概念：**

| 成员 | 对应 Tableau 概念 | 说明 |
|------|-------------------|------|
| `Label` | 节点上的概念集合 | 如 `{A, ∃R.B, ¬C}`，Tableau 算法的所有规则都围绕它展开 |
| `Neighbour` | 角色边 `R(x, y)` | 存储该节点的所有角色边，是处理 `∀` 和 `∃` 规则的依据 |
| `Blocker` / `pBlocked` / `dBlocked` | 阻塞机制 | 保证算法终止。`Blocker` 指向阻塞者节点，`pBlocked` 表示被"净化"（间接阻塞），`dBlocked` 表示直接阻塞 |
| `cached` | 模型缓存 | 缓存该节点代表的模型片段，加速包含关系测试 |
| `nominalLevel` | 名义节点标记 | 区分名义节点（OWL 中指名道姓的个体）与普通块节点，名义节点不能随意合并 |

#### 2. dlCompletionTreeArc.h —— 边的定义

这个文件定义了 `DlCompletionTreeArc` 类。在 Tableau 算法的 ABox（断言盒）里，它代表的就是 **`R(x, y)`（个体间的角色关系）**。

**核心成员变量：**

```cpp
protected:
    DlCompletionTree* Node = nullptr;  // 1. 箭头指向谁？（指向的目标节点）
    const TRole* Role = nullptr;       // 2. 这条线上标着什么标签？（比如角色 R）
    DepSet depSet;                     // 3. 这条边依赖哪些"决策"产生的？（用于回溯）
    DlCompletionTreeArc* Reverse = nullptr; // 4. 反向的边在哪里？（用于双向查找）
    bool SuccEdge = true;              // 5. 这条边是"向下"（Succ）还是"向上"（Pred）？
```

**对应 Tableau 概念的关键点：**

##### (1) 双向性（`Reverse`）

在 Tableau 推理中，经常需要知道**"谁指向了我"**。如果只存单向的 `x -> y`，当算法在处理 `y` 时，就不知道是谁带来了它。

FaCT++ 采用**双向边设计**（存了 `Reverse` 反向指针），这使得无论从哪一头都能快速找到另一头，避免在庞大的图中进行低效的全局搜索。

##### (2) 边被"合并"（`isIBlocked` 检查）

```cpp
bool isIBlocked ( void ) const { return (Role == nullptr); }
```

在 Tableau 算法的 **`≤`-规则（至多限制）** 中，为了满足"最多 n 个邻居"的约束，如果多了一个，需要把两个节点**合并（Merge）**。合并时，其中一条边会被"删除"。

在 FaCT++ 里，删除边**不是真的删掉指针**（那样太耗时且容易内存泄漏），而是把这条边上的 **`Role` 直接置为 `nullptr`**！这就好比这条铁路虽然还在，但我把铁轨抽掉了，逻辑上它就不通了。

`isIBlocked()` 返回 `true` 就代表"这是一条废弃的边"。这种操作非常快，是性能优化的高招。

##### (3) 依赖集（`DepSet`）

`depSet` 记录了这条边是由哪些**"非确定性分支"**（例如 `⊔`-规则的选择）产生的。如果这条边导致了冲突，推理机就能通过这个依赖集判断应该**回溯到哪个分支点**，而不是从头开始。

### 第二站：checkSatisfiability —— Tableau 主循环

```cpp
bool DlSatTester :: checkSatisfiability ( void )
{
    unsigned int loop = 0;
    for (;;)
    {
        if ( curNode == nullptr )
        {
            if ( TODO.empty() )
            {
                if ( performAfterReasoning() )     // 处理公平性等
                    if ( tunedRestore() )
                        return false;
                if ( TODO.empty() )
                    return true;
            }

            const ToDoEntry* curTDE = TODO.getNextEntry ();  // 取出最高优先级任务
            curNode = curTDE->Node;
            curConcept = curNode->label().getConcept(curTDE->offset);
        }

        if ( ++loop == 5000 ) { /* 超时检查 */ }

        if ( commonTactic() )     // 执行规则，若返回 true 表示发生冲突
        {
            if ( tunedRestore() ) // 尝试回溯，若失败则不可满足
                return false;
        }
        else
            curNode = nullptr;
    }
}
```

|--------------|--------------|

| `∀`-规则（全称） | `commonTacticBodyAll` 沿边传播概念 |

### 关键设计亮点总结

| 设计亮点 | 说明 |
|----------|------|
| **优先级驱动的 TODO 队列** | FaCT++ 区别于标准 Tableau 的重要优化，通过优先级调度提升搜索效率 |
| **双向边设计** | 通过 `Reverse` 指针实现双向查找，避免全局搜索 |
| **逻辑删除** | 合并边时将 `Role` 置为 `nullptr`，而非真正删除指针，高效且安全 |
| **依赖集回溯** | `DepSet` 记录分支决策，实现智能回溯（Backjumping）而非简单回溯 |
| **阻塞机制** | 通过 `Blocker` / `pBlocked` / `dBlocked` 实现算法终止保证 |
| **模型缓存** | `cached` 标记加速包含关系测试 |
